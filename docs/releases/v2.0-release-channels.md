# RTPSC v2.0 Release Channels

## Purpose

The v2.0 release registry separates engineering velocity from production accountability. A channel is not merely a label: it defines the canonical tag, semantic package version, intended audience, deployment environment, source-branch policy, support obligation, and permitted promotion path.

| Channel | Canonical tag | Semantic version | Intended use |
|---|---|---:|---|
| Developer | `v2.0-dev` | `2.0.0-dev.0` | Internal engineering and continuously integrated validation |
| Alpha | `v2.0-alpha` | `2.0.0-alpha.0` | Early unstable architecture and integration proof |
| Beta | `v2.0-beta` | `2.0.0-beta.0` | Feature-complete acceptance, security, accessibility, and performance testing |
| Release Candidate | `v2.0-rc1` | `2.0.0-rc.1` | Frozen production-candidate validation |
| Stable | `v2.0-stable` | `2.0.0` | General production release after mandatory gates pass |
| Long-Term Support | `v2.0-lts` | `2.0.0-lts.0` | Extended security, compliance, and critical reliability maintenance |
| Enterprise | `v2.0-enterprise` | `2.0.0-enterprise.0` | Hardened enterprise distribution and governance profile |
| Hotfix | `v2.0-hotfix` | `2.0.0-hotfix.0` | Incident-linked emergency patch lane |

## Commands

```bash
node scripts/release-channel.mjs validate
node scripts/release-channel.mjs list
node scripts/release-channel.mjs show enterprise --json
node scripts/release-channel.mjs manifest alpha --output build/releases/v2.0-alpha.json
node scripts/release-channel.mjs promote rc1 stable
```

## Release controls

1. The registry in `config/release-channels.json` is the source of truth.
2. Every release begins from an approved source branch and a specific commit SHA.
3. CI must complete lint, test, and build gates before publication.
4. The release manifest is uploaded as immutable workflow evidence.
5. Stable, LTS, enterprise, and hotfix publication should use protected GitHub environments with required reviewers.
6. Existing tags are never moved or overwritten.
7. A hotfix must be linked to an incident or security record and reconciled back into every affected supported line.
8. Production publication does not authorize live IRS, banking, identity, or other restricted integrations unless their separate legal, security, credential, and provider gates are satisfied.

## Promotion map

```text
feature/develop -> dev -> alpha -> beta -> rc1 -> stable -> lts -> enterprise
                         \       \       \        \       \          \
                          +-------+-------+--------+-------+----------> hotfix
```

Promotion is fail-closed. The CLI rejects transitions not explicitly listed in the registry.

## GitHub publication workflow

`.github/workflows/release-channel.yml` provides a manually approved publication path. It validates the selected channel, installs dependencies, executes repository quality gates, generates the release manifest, uploads evidence, and—only when `publish=true`—creates the immutable Git tag and GitHub release.

The workflow does not silently deploy restricted external integrations. AWS deployment remains governed by the repository's deployment workflows, environment approvals, OIDC roles, secrets, and production acceptance gates.
